13DHCP, DNS & weitere Dienste

Relevanz ★★★auch in GA 1Lernzeit ca. 100 min
AUF EINEN BLICK
  • DHCP (UDP 67 Server / 68 Client): DORA = Discover → Offer → Request → Acknowledge. Über Routergrenzen nur mit DHCP-Relay.
  • DNS (Port 53) übersetzt Namen in IP-Adressen. Client fragt rekursiv, der DNS-Server löst iterativ auf (Root → TLD → autoritativer Server).
  • Records: A (IPv4) · AAAA (IPv6) · CNAME (Alias) · MX (Mailserver → Hostname) · NS · SOA · PTR (Reverse) · TXT (SPF, DKIM, DMARC) · SRV (Dienste, z. B. AD).
  • Ping auf IP klappt, auf Namen nicht → DNS-Problem.

DHCP

SchrittRichtungInhalt
DiscoverClient → Broadcast„Gibt es einen DHCP-Server?“ (Quelle 0.0.0.0, Ziel 255.255.255.255)
OfferServer → ClientAngebot: IP-Adresse, Maske, Gateway, DNS, Lease-Dauer
RequestClient → Broadcast„Ich nehme das Angebot von Server X“ (andere Server wissen Bescheid)
AcknowledgeServer → ClientBestätigung, Adresse ist verbindlich
  • Lease: Die Adresse ist geliehen. Nach 50 % der Zeit verlängert der Client beim selben Server.
  • Bereich (Scope) mit Ausschlüssen (statische Server/Drucker) und Optionen: Router/Gateway (Option 3), DNS-Server (6), Domänenname (15).
  • Reservierung: feste IP für eine bestimmte MAC-Adresse (Drucker, APs) – zentral verwaltet statt manuell.
  • DHCP-Relay (IP-Helper): Broadcasts enden am Router. Der Router leitet DHCP-Anfragen aus einem VLAN per Unicast an den zentralen DHCP-Server weiter.
  • Kein DHCP erreichbar → Windows vergibt sich eine APIPA-Adresse 169.254.x.x.
  • DHCP-Snooping am Switch blockiert fremde („rogue“) DHCP-Server.

Der Router signalisiert per Flags im Router Advertisement: M-Flag (Managed) = Adresse per DHCPv6, O-Flag (Other) = Zusatzinfos per DHCPv6. Das Default-Gateway kommt bei IPv6 immer aus dem Router Advertisement (Link-Local-Adresse des Routers), nie aus DHCPv6.

DNS

Hierarchie: Root (.) → Top-Level-Domain (.de, .com) → Second-Level-Domain (beispiel.de) → Subdomain/Host (www). Ein FQDN ist der vollständige Name bis zur Wurzel: www.beispiel.de.

  1. Client prüft Cache und hosts -Datei, dann fragt er seinen konfigurierten DNS-Server (rekursive Anfrage: „Liefere mir die fertige Antwort“).
  2. Der DNS-Server (Resolver) fragt, falls nicht im Cache, iterativ: Root-Server → Verweis auf .de-Server → Verweis auf den autoritativen Server von beispiel.de → Antwort.
  3. Der Resolver speichert die Antwort für die Dauer der TTL im Cache und gibt sie an den Client.
RecordFunktionBeispiel
AName → IPv4www IN A 203.0.113.10
AAAAName → IPv6www IN AAAA 2001:db8::10
CNAMEAlias → anderer Nameshop IN CNAME www.beispiel.de.
MXMailserver der Domain, mit Priorität (kleiner = bevorzugt); zeigt auf einen Hostnamen@ IN MX 10 mail.beispiel.de.
NSautoritative Nameserver der Zone@ IN NS ns1.beispiel.de.
SOAVerwaltungsdaten der Zone (primärer NS, Admin-Kontakt, Seriennummer, Timer)genau einer pro Zone
PTRIP → Name (Reverse Lookup, Zone in-addr.arpa)10.113.0.203.in-addr.arpa. PTR www.beispiel.de.
TXTText, z. B. SPF, DKIM-Schlüssel, DMARC, Domain-Verifizierung@ IN TXT "v=spf1 mx -all"
SRVDienst mit Port (z. B. Domain Controller, SIP)_ldap._tcp.firma.local
  • Primärer / sekundärer DNS-Server: Die Zone wird per Zonentransfer (TCP 53) vom primären auf den sekundären Server kopiert → Redundanz.
  • Lastverteilung: mehrere A-Records für einen Namen (Round Robin).
  • DNSSEC: signiert DNS-Antworten kryptografisch → Authentizität und Integrität (Schutz vor DNS-Spoofing/Cache Poisoning). Verschlüsselt aber nichts!
  • DoT (DNS over TLS, Port 853) und DoH (DNS over HTTPS, 443) verschlüsseln die Anfrage → Vertraulichkeit.
TYPISCHE PRÜFUNGSAUFGABE: NSLOOKUP AUSWERTEN
C:\> nslookup www.beispiel.de
Server:   dns1.firma.local
Address:  192.168.1.10
Nicht autorisierende Antwort:
Name:     www.beispiel.de
Addresses: 2001:db8::10
           203.0.113.10

Auswertung: Der verwendete DNS-Server ist 192.168.1.10. „Nicht autorisierend“ = die Antwort stammt aus dem Cache bzw. von einem anderen Server, nicht vom zuständigen Nameserver der Zone. Es gibt einen AAAA- und einen A-Record. Bei DNS request timed out ist der DNS-Server nicht erreichbar (Dienst aus, falsche IP, Firewall, fehlende Route).

FALLEN
  • Rekursiv ↔ iterativ vertauschen. Merkhilfe: Rekursiv = Rundum-Service für den Client, iterativ = Schritt für Schritt mit Verweisen.
  • Der MX-Record zeigt nie direkt auf eine IP-Adresse und nicht auf einen CNAME.
  • DNSSEC ≠ Verschlüsselung.

DNSSplit-horizon DNS = gleicher Name, andere Antwort je nach Fragendem: intern private IP, extern öffentliche IP 1× · Forwarder = Weiterleitung an Provider-DNS: Cache, weniger eigene Anfragen 1× · Öffentliche DNS verbieten = interne Namen nicht auflösbar, Filter und Protokollierung würden umgangen 1× · DNS-Spoofing = gefälschte Antwort leitet auf falsche Seite → Schutz DNSSEC (Signatur: Authentizität + Integrität) 1×
DHCP & ARPDiscover als Broadcast = Client kennt weder eigene IP noch Server 1× · Falsche Parameter = zweiter (Rogue-)DHCP-Server im Netz oder statisch eingetragen 1× · ARP-Poisoning = gefälschte ARP-Antworten lenken Verkehr über den Angreifer (Man-in-the-Middle); Schutz: Dynamic ARP Inspection, Port-Security 1× · Gratuitous ARP = Client kündigt nach DHCP seine IP an → Doppelvergabe wird erkannt, ARP-Tabellen aktualisiert 1×

ÜBUNGEN

Ü13.1 Welcher Record ist nötig? a) Mails an @firma.de sollen bei mail.firma.de ankommen · b) intranet.firma.de soll auf server03.firma.de verweisen · c) Ein Mailserver prüft, ob zur IP 203.0.113.25 der Name mail.firma.de gehört · d) Nur der Server 203.0.113.25 darf Mails für firma.de versenden.

Ü13.2 Ein neuer Standort (VLAN 40) soll den zentralen DHCP-Server im Rechenzentrum nutzen. Was muss konfiguriert werden?

Lösungen Kapitel 13

Ü13.1 a) MX (plus A-Record für mail.firma.de) · b) CNAME · c) PTR (Reverse Lookup) · d) TXT mit SPF: v=spf1 ip4:203.0.113.25 -all

Ü13.2 Auf dem Gateway von VLAN 40 ein DHCP-Relay (IP-Helper) mit der Adresse des DHCP-Servers; auf dem DHCP-Server einen Bereich für das Netz von VLAN 40 mit Optionen (Gateway, DNS); Firewall muss UDP 67/68 zwischen Relay und Server erlauben.
