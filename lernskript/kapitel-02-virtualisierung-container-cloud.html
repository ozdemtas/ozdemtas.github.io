2Virtualisierung, Container & Cloud

Relevanz ★★★auch in GA 2Lernzeit ca. 90 min
AUF EINEN BLICK
  • Hypervisor Typ 1 läuft direkt auf der Hardware (ESXi, Hyper-V, Proxmox VE). Typ 2 läuft auf einem Betriebssystem (VirtualBox, VMware Workstation).
  • Container teilen sich den Kernel des Hosts → leichter und schneller als VMs, aber schwächer isoliert.
  • Snapshot ist kein Backup.
  • IaaS / PaaS / SaaS: Je weiter rechts, desto mehr verwaltet der Anbieter.
  • Skalierung: horizontal (mehr Server, scale out) vs. vertikal (stärkerer Server, scale up).

Virtualisierung: Vor- und Nachteile

  • Single Point of Failure: Host fällt aus → alle VMs betroffen (Lösung: Cluster + HA)
  • Overhead durch Hypervisor
  • Komplexere Administration, Know-how nötig
  • Lizenzkosten (z. B. pro Kern)
  • Ressourcenkonkurrenz bei Überbuchung

Leistunghoch, wenig Overheadgeringer

Wichtige Begriffe

  • Snapshot: Zustand einer VM zu einem Zeitpunkt. Liegt auf demselben Storage und hängt an der Original-Disk. Fällt der Storage aus, ist beides weg. Deshalb kein Backup, sondern eine Absicherung vor Änderungen (z. B. vor einem Update). Nicht wochenlang stehen lassen, sonst leidet die Performance.
  • Live-Migration: laufende VM ohne Unterbrechung auf einen anderen Host verschieben. Voraussetzung: gemeinsamer Storage (Shared Storage) oder Replikation, kompatible CPUs.
  • Hochverfügbarkeit (HA): Fällt ein Host aus, starten seine VMs automatisch auf anderen Hosts neu. Braucht einen Cluster, sinnvollerweise ab 3 Knoten (Quorum/Mehrheitsentscheidung gegen „Split Brain“).
  • Overcommitment: Den VMs mehr virtuelle Ressourcen zuweisen, als physisch vorhanden sind. Spart Hardware, riskiert aber Engpässe.
  • Template / Klon: vorkonfigurierte Vorlage, aus der neue VMs in Minuten entstehen.

Virtualisierungsarten und Cluster

ArtFunktionsweiseBewertung
VollvirtualisierungGast-Betriebssystem läuft unverändert; der Hypervisor stellt komplette virtuelle Hardware bereit, heute hardwareunterstützt (Intel VT-x / AMD-V)jedes OS möglich (auch Windows), Standard bei ESXi, Hyper-V, KVM
ParavirtualisierungGast-OS ist angepasst und spricht den Hypervisor direkt an, heute v. a. als paravirtualisierte Treiber (VirtIO für Netz und Disk)weniger Overhead, bessere I/O-Leistung; Gast muss es unterstützen
Containervirtualisierungkeine eigene virtuelle Hardware, gemeinsamer Kernel des Hosts (Docker, LXC)sehr leicht, aber nur gleicher Kernel-Typ
Cluster-BetriebsartFunktionsweiseBewertung
Active/Passiveein Knoten arbeitet, der zweite steht bereit und übernimmt bei Ausfall (Failover); Knoten prüfen sich per Heartbeateinfach, sichere Reserve; Standby-Hardware ist ungenutzt

Failback = Rückkehr auf den ursprünglichen Knoten nach der Reparatur. Ein Cluster schützt vor Hardwareausfall, nicht vor Datenverlust: Backup bleibt Pflicht.

Netzwerkmodi von VMs

Der Hypervisor stellt einen virtuellen Switch bereit. Wie die virtuelle Netzwerkkarte einer VM angebunden wird, entscheidet, wer die VM erreicht und was sie selbst erreicht.

ModusFunktionsweiseErreichbarkeitTypischer Einsatz
Bridge (Netzwerkbrücke)VM hängt direkt im physischen LAN, bekommt eine eigene IP aus dem LANwie ein eigener Rechner im NetzServer-VMs
NATVM liegt in einem privaten Netz hinter dem Host und nutzt dessen IP nach außenkommt ins LAN/Internet, von außen nur per PortweiterleitungClient- und Test-VMs
Host-onlyeigenes Netz nur zwischen Host und VMskein Zugang nach außenLabor, Schulung

VLANs in der Virtualisierung: Der Uplink des Hosts ist ein Trunk (tagged); am virtuellen Switch bekommt jede VM ihr VLAN. So landen z. B. Webserver-VM und Datenbank-VM auf demselben Host trotzdem in getrennten Netzen.

TYPISCHE PRÜFUNGSAUFGABE

a) Eine Test-VM soll Updates aus dem Internet laden, aber im Firmennetz nicht erreichbar sein. b) Eine Webserver-VM soll für alle Clients im LAN erreichbar sein. Welcher Netzwerkmodus jeweils?

Lösung: a) NAT: Die VM kommt über die Host-IP nach außen, ist von außen aber nicht direkt erreichbar. b) Bridge (bzw. eigenes VLAN am virtuellen Switch): Die VM erhält eine eigene Adresse und ist wie ein physischer Server erreichbar.

Container

Ein Container verpackt eine Anwendung mit allen Bibliotheken, nutzt aber den Kernel des Host-Systems. Er startet in Sekunden und braucht wenig Ressourcen. Werkzeuge: Docker/Podman (Container ausführen), Image (Vorlage), Registry (Ablage für Images), Kubernetes (Orchestrierung vieler Container auf vielen Hosts).

Kriterien zur Auswahl eines Cloud-Anbieters: Datenschutz (Serverstandort EU, AV-Vertrag, Zertifizierungen wie ISO 27001/BSI C5), Sicherheit, Verfügbarkeit laut SLA, Kosten-Nutzen (Preismodell, Datentransferkosten), Integration in bestehende Systeme (Schnittstellen, Identitätsverwaltung), Skalierbarkeit, Support, Exit-Strategie (Datenexport, kein Lock- in).

FALLE: DATENSCHUTZ IN DER CLOUD

Werden personenbezogene Daten in die Cloud ausgelagert, braucht es einen Auftragsverarbeitungsvertrag (AVV, Art. 28 DSGVO). Bei Speicherung außerhalb der EU muss ein angemessenes Datenschutzniveau gesichert sein. In Prüfungen gibt es Punkte für „Rechenzentrumsstandort in der EU wählen“.

Skalierung

  • Vertikal (scale up): mehr CPU/RAM für einen Server. Einfach, aber begrenzt und oft mit Neustart.
  • Horizontal (scale out): weitere Server hinzufügen, Last per Load Balancer verteilen. Fast unbegrenzt, erhöht zugleich die Ausfallsicherheit.
TYPISCHE PRÜFUNGSAUFGABE

Die Firma will ihre Mailserver-Landschaft ablösen und keine eigenen Server mehr betreiben. Welches Cloud-Modell passt? Begründen Sie und nennen Sie ein Risiko.

Lösung: SaaS (z. B. gehostetes Exchange/Microsoft 365), denn der Anbieter betreibt Infrastruktur, Betriebssystem und Anwendung; das Unternehmen verwaltet nur noch Benutzer und Daten. Risiko: Abhängigkeit von Internetverbindung und Anbieter, Datenschutz (AVV, Serverstandort).

ÜBUNGEN

Ü2.1 Ordne zu (IaaS/PaaS/SaaS): a) Entwickler wollen nur Code hochladen, ohne sich um Server zu kümmern. b) Die IT braucht kurzfristig 20 virtuelle Server für einen Lasttest. c) Die Buchhaltung nutzt eine Online-Lohnabrechnung im Browser.

Ü2.2 Ein Kollege sagt: „Wir brauchen kein Backup, wir machen jede Nacht Snapshots.“ Nimm Stellung (2 Argumente).

Ü2.3 Nenne zwei Gründe, warum man für einen HA-Cluster mindestens drei Knoten einsetzt.

Lösungen Kapitel 2

Ü2.1 a) PaaS · b) IaaS · c) SaaS

Ü2.2 Snapshots liegen auf demselben Storage wie die VM: Bei Hardwaredefekt, Ransomware oder Löschen des Storage sind sie mit weg. Sie sind abhängig von der Original-Disk, nicht auslagerbar (3-2-1-Regel nicht erfüllt) und verschlechtern auf Dauer die Performance. Ein echtes Backup auf getrennten Medien ist nötig.

Ü2.3 Quorum: Bei Ausfall eines Knotens haben die zwei übrigen noch die Mehrheit und verhindern „Split Brain“. Außerdem kann die Last eines ausgefallenen Knotens auf mehrere andere verteilt werden (N+1-Redundanz).
